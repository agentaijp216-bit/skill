# ตั้ง project tracker จากสรุป kickoff

โครงสร้างที่ skill นี้สร้าง คือสิ่งที่ skill อื่นทั้งชุดจะอ่านไปอีกสิบสัปดาห์ ผู้ใช้จึงอนุมัติจากของที่กดดูได้จริง

## ขั้นที่ 1 — อ่านสรุป kickoff

input คือสรุปประชุมที่ได้จาก skill `meeting-summary` ถ้าได้รับ transcript ดิบ ให้เรียก `meeting-summary` ก่อน แล้วค่อยกลับมาที่นี่

ดึงจากสรุปให้ครบ ตามลำดับหัวข้อที่หน้าโครงการจะใช้จริง: เป้าหมาย ขอบเขต สิ่งที่ไม่อยู่ในขอบเขต วันสำคัญ แผนเฟสทั้งโครงการ (มีกี่เฟส แต่ละเฟสชื่ออะไร จบวันไหน ตอนนี้อยู่เฟสไหน และทั้งโครงการจบวันไหน) ทีมและบทบาท ชื่อลูกค้าและผู้ติดต่อพร้อมช่องทางติดต่อ จังหวะการรายงาน โทนการสื่อสาร ความเสี่ยง และรายการงานที่ตกลงกันพร้อมผู้รับผิดชอบกับวันที่รับปาก

ตั้งชื่อโครงการที่จะใช้ไว้ก่อน การเช็คว่าชื่อนี้มีอยู่แล้วหรือยัง ทำในขั้นที่ 2 หลังรู้หน้าปลายทาง

## ขั้นที่ 2 — ซักจนพิมพ์เขียวเต็ม

เป้าหมายของการซักคือเก็บทุกอย่างที่**พิมพ์เขียว**ในขั้นที่ 3 ต้องมีเพื่อให้สมบูรณ์ ช่องไหนที่ยังเติมไม่ได้ คือคำถามที่ยังต้องถาม

ถามทีละคำถาม รอคำตอบก่อนถามข้อถัดไป และถามเฉพาะข้อมูลที่ยังขาด สิ่งใดที่อ่านได้จาก Notion หรือจากไฟล์ที่ได้รับแล้ว ให้ไปอ่านเอง เมื่อได้ครบแล้ว หยุดถามทันที แล้วลงมือทำ

คำตอบใช้ได้ต่อเมื่อเติมช่องในพิมพ์เขียวได้ — ชื่อคน หนึ่งชื่อ และวันที่ เป็นวันที่จริง ไม่ใช่ "สิ้นเดือน" วันจบเฟสและวันจบโครงการก็เป็นวันที่จริงเหมือนกัน

skill นี้เริ่มไม่ได้ถ้ายังไม่มีหน้าปลายทางใน Notion ผู้ใช้ยังไม่ได้ให้มา ให้ถามข้อ 1 แล้วรอ ห้ามสร้างอะไรโดยไม่ระบุหน้าแม่ เพราะของจะไปโผล่ที่ระดับ workspace แล้วไม่มี skill ไหนหาเจอ

ชุดคำถามของ skill นี้:

1. จะสร้างไว้ที่หน้าไหนใน Notion
2. วางแบบไหนในหน้านั้น — รายละเอียดข้างล่าง
3. โครงการนี้มีกี่เฟส แต่ละเฟสชื่ออะไรและจบวันไหน ตอนนี้อยู่เฟสไหน แล้วทั้งโครงการจบวันไหน
4. ชื่อบริษัทลูกค้า และผู้ติดต่อแต่ละคน — ชื่อ บทบาท ช่องทางติดต่อ
5. ขอบเขตที่ยังคลุมเครือหลังอ่านสรุปแล้ว
6. ระบุงานที่ขาดผู้รับผิดชอบหรือวันที่รับปากด้วยตัวเอง แล้วถามเฉพาะงานเหล่านั้นทีละงานว่าใครรับ และรับปากวันไหน
7. สัดส่วนเวลาของแต่ละคน มีใครไม่ได้ทำเต็มเวลาไหม

### ช่องที่เติมไม่ได้ — สองป้าย ไม่ใช่ป้ายเดียว

แยกป้ายตามสิ่งที่ต้องทำต่อ ไม่ใช่ตามว่าช่องว่างหรือไม่ว่าง:

- **ผู้ใช้ไม่ทราบ** — คำตอบมีอยู่จริงในโลกแล้ว แต่ยังไม่อยู่ในมือผู้ใช้ ต้องไปเอามาจากลูกค้าหรือ BA (ชื่อบริษัทลูกค้า ช่องทางติดต่อ จำนวนเฟส วันจบเฟส วันจบโครงการ)
- **ยังไม่ระบุ** — ยังไม่มีคำตอบ เพราะยังไม่มีใครตัดสิน (ผู้รับผิดชอบ วันที่รับปาก)

ทั้งสองแบบ ถามครั้งเดียว ตอบไม่ได้ ใส่ป้ายลงในช่องนั้นแล้วเดินต่อทันที ห้ามถามซ้ำ ห้ามเอาค่าที่เดาเองไปใส่แทนป้าย (ค่าที่อนุมานจากสรุปได้ ให้ใส่แล้วติดป้าย **อนุมาน** ตั้งแต่ต้น ไม่ใช่รอให้ผู้ใช้ตอบไม่ได้ก่อนแล้วค่อยเดา) และห้ามตัดหัวข้อนั้นทิ้งเพราะยังเติมไม่ได้ ช่องที่เห็นว่าง คือสิ่งที่ทำให้ได้กลับมาเติม ทุกช่องที่ติดป้าย ไปโผล่ในรายการค้างของพิมพ์เขียว แยกกันสองกลุ่มตามป้าย

### ที่วางของข้อ 2

ได้หน้าปลายทางจากข้อ 1 แล้ว เปิดอ่านก่อนว่าในหน้านั้นมีอะไรอยู่ เจอหน้าโครงการชื่อเดียวกันอยู่แล้ว ให้ส่งลิงก์ให้ผู้ใช้แล้วถามว่าจะเติมเข้าหน้าเดิมหรือสร้างใหม่ ก่อนถามข้อนี้ต่อ

จากนั้นเสนอสองทางให้ผู้ใช้เลือก อธิบายด้วยผลที่ตามมา ไม่ใช่ด้วยชื่อทาง:

- **ลงในหน้าที่ให้มาเลย** — หน้านั้นกลายเป็นหน้าโครงการ หัวข้อ config ต่อท้ายของเดิมในหน้านั้นโดยไม่ลบอะไร database ทั้งสี่อยู่ใต้หน้านั้น เหมาะกับคนที่ดูแลโครงการเดียว
- **สร้างหน้าย่อยข้างใน** — สร้างหน้าใหม่ชื่อโครงการไว้ในหน้าที่ให้มา หน้าใหม่คือหน้าโครงการ database ทั้งสี่อยู่ใต้หน้าใหม่ ส่วนหน้าที่ให้มากลายเป็นหน้ารวมโครงการ เหมาะกับคนที่ดูแลหลายโครงการพร้อมกัน เพราะโครงการหน้าถัดไปมาลงที่เดียวกันได้โดยไม่ชนกัน

เสนอทางที่น่าจะใช่ก่อนตามสิ่งที่เห็นในหน้านั้น — มีหน้าย่อยที่เป็นโครงการอื่นอยู่แล้ว หรือชื่อหน้าเป็นคำรวมอย่าง Projects ให้เสนอ **สร้างหน้าย่อยข้างใน** หน้าว่างหรือมีแต่โน้ตของโครงการนี้ ให้เสนอ **ลงในหน้าที่ให้มาเลย** ไม่เข้าทั้งสองแบบ ให้เสนอ **สร้างหน้าย่อยข้างใน** เพราะย้ายกลับทีหลังง่ายกว่า แล้วให้ผู้ใช้ยืนยันหรือเปลี่ยน คำตอบนี้เป็นตัวกำหนด page tree ที่วาดในพิมพ์เขียว

### แผนเฟสของข้อ 3

ถามเป็นข้อเดียว ไม่ต้องไล่ถามทีละเฟส ต้องการแค่สามอย่างต่อหนึ่งเฟส: ลำดับ ชื่อ และวันจบ บวกอีกสองอย่างของทั้งโครงการ — ตอนนี้อยู่เฟสไหน และโครงการจบวันไหน

ห้ามคำนวณวันบัฟเฟอร์ ระยะห่างระหว่างเฟส หรือความเสี่ยงว่าเฟสไหนจะชนเฟสไหน ให้ผู้ใช้ หน้าที่ของ skill นี้คือวางวันจบทั้งหมดไว้ให้เห็นพร้อมกันหน้าเดียว ผู้ใช้ตัดสินเองว่าเฟสที่บวมอยู่ยังบวมได้อีกเท่าไหร่

ผู้ใช้ตอบไม่ได้ว่ามีกี่เฟส ให้ลงตารางแถวเดียว — "เฟส 1" ทำเครื่องหมายว่าเป็นเฟสปัจจุบัน วันจบเป็น "ผู้ใช้ไม่ทราบ" — แล้วเพิ่มบรรทัด "จำนวนเฟสทั้งหมด: ผู้ใช้ไม่ทราบ" ไว้ใต้ตาราง ห้ามข้ามหัวข้อแผนเฟสไปเฉยๆ

### ผู้ติดต่อลูกค้าของข้อ 4

สรุปที่บอกแค่บทบาท ("ฝ่ายไอทีของลูกค้า") ยังไม่นับว่าครบ ต้องได้ชื่อคน และช่องทางที่ติดต่อได้จริงพร้อมระบุว่าเป็นช่องทางอะไร — อีเมล เบอร์โทร Line หรือกลุ่มแชท

ชื่อบริษัทลูกค้าเป็นคนละช่องกับชื่อผู้ติดต่อ ถามให้ได้ทั้งสองอย่าง ไม่ทราบอันไหน ติดป้าย **ผู้ใช้ไม่ทราบ** เฉพาะอันนั้น

## ขั้นที่ 3 — สร้างพิมพ์เขียวแล้วขออนุมัติ

ก่อนวาด ตรวจว่าทุกแถวมีผู้รับผิดชอบและวันที่รับปากครบ ทุกเฟสมีวันจบ และผู้ติดต่อทุกคนมีช่องทาง ช่องไหนที่ยังว่าง ให้ย้อนไปซักในขั้นที่ 2 จนเต็ม ถ้าผู้ใช้ยังตอบไม่ได้หลังถามครั้งเดียว ให้ใส่ป้ายตามกติกาสองป้ายข้างบน รวมไว้เป็นรายการค้างในพิมพ์เขียว แล้วเดินต่อ

จากนั้นสร้างไฟล์ HTML หน้าเดียวที่จำลอง workspace ที่กำลังจะสร้าง แล้ว publish เป็น artifact **พิมพ์เขียว**คืออันนั้น ไม่ใช่ข้อความในแชท

ในแชทเขียนสั้นๆ อย่างเดียว: ลิงก์พิมพ์เขียว เรื่องที่ผู้ใช้ต้องตัดสิน และสิ่งที่ agent อนุมานเอง จากนั้นถามขออนุมัติแล้วรอคำตอบ ยังไม่แตะ Notion

พิมพ์เขียวต้องอ่านแล้วเหมือนเปิด Notion ไม่ใช่เหมือนอ่านเอกสารสเปก:

- **sidebar** เป็น page tree จริงตามที่วางไว้ในข้อ 2 — เลือกลงในหน้าที่ให้มา วาดเป็น หน้าที่ให้มา (คือหน้าโครงการ) → database ทั้งสี่ / เลือกสร้างหน้าย่อย วาดเป็น หน้าที่ให้มา → หน้าโครงการ → database ทั้งสี่
- **หน้าโครงการ** เรนเดอร์อย่างหน้า Notion — icon ชื่อเรื่อง page properties (มี **ลูกค้า** เป็นชื่อองค์กร) แล้วตามด้วยหัวข้อ config เป็น block จริง เลือกลงในหน้าที่ให้มา ให้วาด block เดิมที่มีอยู่ในหน้านั้นไว้ด้วย ผู้ใช้จะได้เห็นว่าของเดิมยังอยู่ครบ (เป้าหมาย ขอบเขต สิ่งที่ไม่อยู่ในขอบเขต วันสำคัญ แผนเฟส ทีมและบทบาทพร้อมสัดส่วนเวลา ผู้ติดต่อลูกค้า จังหวะการรายงาน โทนการสื่อสาร ความเสี่ยง) หน้านี้คือ config ที่ skill อื่นอ่าน ผู้ใช้จึงต้องตรวจ**ถ้อยคำจริง** ไม่ใช่ตรวจบทสรุปของถ้อยคำ
- **ตาราง "แผนเฟส"** อยู่ถัดจาก "วันสำคัญ" คอลัมน์ เฟสที่ · ชื่อเฟส · วันจบ หนึ่งแถวต่อหนึ่งเฟส เรียงตามลำดับเฟส เฟสที่กำลังทำอยู่ทำเครื่องหมายให้เห็นทันทีว่าเป็นเฟสปัจจุบัน ปิดท้ายด้วยบรรทัด **วันจบโครงการ** ใต้ตาราง ตารางนี้ตอบคำถามเดียว — โครงการมีกี่เฟส และแต่ละเฟสต้องจบวันไหน เห็นพร้อมกันหน้าเดียวโดยไม่ต้องเปิดที่อื่น
- **ตาราง "ผู้ติดต่อลูกค้า"** คอลัมน์ ชื่อ · บทบาท · ช่องทางติดต่อ หนึ่งแถวต่อหนึ่งคน ช่องทางบอกด้วยว่าเป็นช่องทางอะไร ไม่ใช่ปล่อยเป็นตัวเลขหรือชื่อบัญชีลอยๆ
- **database "งาน"** เป็น kanban ที่ใช้งานได้ — group ตามสถานะ การ์ดละหนึ่งงานแสดงผู้รับผิดชอบ วันที่รับปาก และเฟส ลากข้ามคอลัมน์ได้ ตัวเลขนับหัวคอลัมน์ขยับตาม และมีแท็บสลับ board / table แบบ view tabs ของ Notion
- **คลิกเข้าไปในแถวได้** — คลิกการ์ดหรือแถวในตาราง เปิด peek panel แบบ Notion แสดง property ครบทุกตัว รวมตัวที่ตั้งใจเว้นว่างไว้ให้ skill อื่นเติมทีหลัง
- **แถว "ประชุม"** เรนเดอร์แบบเดียวกัน — property อยู่ข้างบน เนื้อหาประชุมครบเจ็ดส่วน (บริบท · สรุป · มติที่ตกลง · สิ่งที่ต้องทำ — ฝั่งเรา · สิ่งที่ต้องทำ — ฝั่งลูกค้า · คำถามค้าง · ความเสี่ยง) อยู่ใน page body ข้างล่าง ตรงที่มันจะอยู่จริง
- **database ที่ยังว่าง** แสดงว่าว่าง พร้อมป้ายบอกว่า skill ไหนเป็นคนเติม และเติมเมื่อไหร่
- **รายการค้าง** แยกสองกลุ่มตามป้าย — **ต้องไปเอาคำตอบมา** (ผู้ใช้ไม่ทราบ) กับ **ต้องตัดสินใจ** (ยังไม่ระบุ) แต่ละรายการบอกว่าค้างอยู่ที่ช่องไหนของอะไร
- **ปุ่ม "แสดงที่มา"** ปิดไว้เป็นค่าเริ่มต้น เปิดแล้วขึ้นสองป้าย: **อนุมาน** ที่ทุกวันที่หรือผู้รับผิดชอบที่ agent เดาเอง ไม่ได้ยินจากในห้อง และ **ข้อจำกัด Notion** ที่ทุกจุดซึ่งโครงสร้างจริงต่างจาก reference ข้างล่าง

พิมพ์เขียวที่ผู้ใช้เคยอนุมัติ ใช้เทียบ**หน้าตา**ได้: https://claude.ai/code/artifact/de4943d6-6864-4e3a-94d8-29aab7759f44 อันนั้นทำก่อนมีแผนเฟสและตารางผู้ติดต่อ จึงไม่มีสองส่วนนั้น ความครบถ้วนให้ยึดรายการข้างบนนี้เป็นตัวตัดสิน เปิดลิงก์ไม่ได้ก็ใช้รายการข้างบนนี้เหมือนกัน

**สัญญาว่าตรงกัน** — พิมพ์เขียวคือภาพของสิ่งที่จะสร้าง ไม่ใช่ภาพประกอบ สิ่งที่ผู้ใช้อนุมัติในพิมพ์เขียว คือสิ่งที่จะถูกสร้างใน Notion ครบทุกฟิลด์ ครบทุกแถว เรียงลำดับเดียวกัน อะไรที่ Notion สร้างตามที่วาดไม่ได้ ห้ามวาดแบบนั้น ให้วาดเป็นสิ่งที่ Notion จะได้จริง แล้วติดป้าย **ข้อจำกัด Notion** ไว้ตรงนั้น

reference ข้างล่างเป็นตัวตัดสินตอน**วาด** พิมพ์เขียวเป็นตัวตัดสินตอน**สร้าง** ถ้าสองอันไม่ตรงกัน แปลว่าวาดผิด ให้แก้พิมพ์เขียวแล้ว publish ใหม่ก่อนขออนุมัติ

## ขั้นที่ 4 — สร้างตามพิมพ์เขียว

เมื่อผู้ใช้อนุมัติแล้ว สร้างตามพิมพ์เขียวทีละส่วน:

1. หน้าโครงการ — เลือกสร้างหน้าย่อย ให้สร้างหน้าใหม่ในหน้าที่ให้มาก่อน เลือกลงในหน้าที่ให้มา ให้เขียนลงหน้านั้นตรงๆ จากนั้นใส่ property **ลูกค้า** กับหัวข้อและถ้อยคำตามที่อยู่ในพิมพ์เขียว
2. ตาราง **แผนเฟส** และตาราง **ผู้ติดต่อลูกค้า** เป็น table block ในหน้าโครงการ จำนวนแถวและถ้อยคำตรงกับพิมพ์เขียว
3. database ทั้งสี่ตัวใต้หน้าโครงการ ตามฟิลด์ใน reference ข้างล่าง ตอนสร้าง database งาน ประกาศตัวเลือกของ select **เฟส** ให้ครบทุกเฟสที่อยู่ในตารางแผนเฟส ไม่ใช่เฉพาะเฟสปัจจุบัน
4. ประชุม kickoff หนึ่งแถวใน database ประชุม เนื้อหาครบเจ็ดส่วนตาม reference ข้างล่าง — สร้างก่อนงาน เพราะทุกแถวงานต้องมี ประชุมที่มา ชี้มาที่แถวนี้
5. งานทุกรายการลง database งาน เรียงลำดับตามพิมพ์เขียว ทุกแถวชี้ ประชุมที่มา ไปที่แถวประชุมที่เพิ่งสร้าง

ช่องที่ติดป้าย **ผู้ใช้ไม่ทราบ** หรือ **ยังไม่ระบุ** ในพิมพ์เขียว ให้เขียนป้ายนั้นลง Notion ตามคำเดิม ไม่ปล่อยช่องว่าง และไม่สลับป้ายกัน ช่องว่างเปล่าใน Notion แปลว่า "รอ skill อื่นมาเติม" ซึ่งคนละความหมายกับป้ายทั้งสอง

เจอว่าสร้างอะไรตามที่พิมพ์เขียวสัญญาไว้ไม่ได้ ให้**หยุดแล้วรายงานผู้ใช้ทันที** ว่าติดตรงไหนและ Notion ให้อะไรแทนได้ แล้วรอคำตอบ ห้ามสร้างของที่ต่างจากพิมพ์เขียวโดยไม่บอก

ปิดงานด้วยลิงก์หน้าโครงการและจำนวนงานที่สร้างจริง

## เสร็จเมื่อ

- ผู้ใช้อนุมัติพิมพ์เขียวแล้ว
- ทุกอย่างใน Notion ตรงกับพิมพ์เขียวที่อนุมัติ — จำนวนแถวใน database งาน เท่ากับจำนวนการ์ดในพิมพ์เขียว ชื่อและลำดับฟิลด์ตรงกัน หัวข้อในหน้าโครงการตรงกัน และ database ครบทั้งสี่ตัว
- หน้าโครงการมีตาราง **แผนเฟส** ครบทุกเฟสตามที่ตอบข้อ 3 พร้อมวันจบของแต่ละเฟส ทำเครื่องหมายเฟสปัจจุบันไว้ และมีวันจบโครงการอยู่ใต้ตาราง ตอบไม่ได้ว่ามีกี่เฟส ต้องเป็นตารางแถวเดียวพร้อมบรรทัด "จำนวนเฟสทั้งหมด: ผู้ใช้ไม่ทราบ" ไม่ใช่ไม่มีหัวข้อนี้
- ทุกแถวใน database งาน มี เฟส และตัวเลือกของ select เฟส ครบทุกเฟสในตารางแผนเฟส
- หน้าโครงการมี property **ลูกค้า** เป็นชื่อองค์กร และตาราง **ผู้ติดต่อลูกค้า** ที่ทุกแถวมีทั้งชื่อ บทบาท และช่องทางติดต่อ หรือเป็น "ผู้ใช้ไม่ทราบ" ที่อยู่ในรายการค้างของพิมพ์เขียวแล้ว
- งานทุกแถวมีทั้งผู้รับผิดชอบและวันที่รับปาก หรือเป็น "ยังไม่ระบุ" ที่อยู่ในรายการค้างของพิมพ์เขียวแล้ว
- ช่องที่เติมไม่ได้ ใช้ป้ายถูกประเภท — "ผู้ใช้ไม่ทราบ" สำหรับของที่ต้องไปเอามา "ยังไม่ระบุ" สำหรับของที่ต้องตัดสิน ไม่ปนกัน
- มีแถวประชุม kickoff หนึ่งแถวใน database ประชุม และเนื้อหาเจ็ดส่วนอยู่ใน page body ของแถวนั้น ไม่ใช่ใน property
- ผู้รับผิดชอบ ใน database งาน เป็น select ที่มีตัวเลือกครบทุกคนในพิมพ์เขียว
- ทุกแถวใน database งาน มี ประชุมที่มา ชี้ไปที่แถวประชุม kickoff
- ถ้อยคำในหัวข้อ config ของหน้าโครงการ ตรงกับที่อยู่ในพิมพ์เขียว
- page tree จริงตรงกับที่วาดไว้ในพิมพ์เขียว — database ทั้งสี่อยู่ใต้หน้าโครงการ หน้าโครงการอยู่ที่เดิมตามที่ตอบข้อ 2 และไม่มีอะไรไปอยู่ที่ระดับ workspace เลือกลงในหน้าที่ให้มา ให้ตรวจด้วยว่า block เดิมในหน้านั้นยังอยู่ครบ

## reference — ฟิลด์ของแต่ละ database

- **งาน** — เติมตอน kickoff: ชื่องาน, ผู้รับผิดชอบ, เฟส, สถานะ, วันที่รับปาก, ประชุมที่มา, อัปเดตล่าสุด (ใส่วันที่ kickoff — ปล่อยว่างแล้ว morning-brief จะจับงานเงียบไม่ได้) / เว้นว่างให้ skill อื่นเติมภายหลัง: วันที่เสร็จจริง, สิ่งที่ติดขัด, สรุปงานล่าสุด (บรรทัดเดียว — รายละเอียดเต็มอยู่ในบันทึกในหน้าการ์ด), บทเรียน
- **ประชุม** — คุณสมบัติ: ชื่อ, วันที่, ประเภท (ภายใน/ลูกค้า), ผู้เข้าร่วม / เนื้อหาเจ็ดส่วนใน page body: บริบท, สรุป, มติที่ตกลง, สิ่งที่ต้องทำ — ฝั่งเรา, สิ่งที่ต้องทำ — ฝั่งลูกค้า, คำถามค้าง, ความเสี่ยง
- **บรีฟเช้า** — วันที่, เนื้อหา
- **สรุปสัปดาห์** — สัปดาห์ที่, เนื้อหา

หน้าโครงการ: property **ลูกค้า** (ชื่อองค์กร) · หัวข้อ config ตามลำดับในขั้นที่ 3 โดย **แผนเฟส** (ตาราง เฟสที่ · ชื่อเฟส · วันจบ + วันจบโครงการ) อยู่ถัดจาก **วันสำคัญ** และ **ผู้ติดต่อลูกค้า** เป็นตาราง ชื่อ · บทบาท · ช่องทางติดต่อ

ข้อจำกัดสามข้อที่ Notion บังคับ เจอจากการรันจริง พิมพ์เขียวต้องวาดตามนี้:

- **เนื้อหายาวเป็น page body ไม่ใช่ property** — property ชนิดข้อความของ Notion จุได้ราว 2,000 ตัวอักษร สรุปประชุม kickoff จริงยาวกว่านั้นหลายเท่า และส่วนที่เกินจะหายไปเงียบๆ ไม่ขึ้น error เนื้อหาเจ็ดส่วนของ ประชุม จึงเป็นหัวข้อใน page body ของแถว skill ที่มาอ่านจะเปิดแถวแล้วเจอเอง
- **ผู้รับผิดชอบ เป็น select ไม่ใช่ person** — property ชนิด person ของ Notion รับได้เฉพาะสมาชิกจริงใน workspace คนในทีมโครงการและผู้ติดต่อฝั่งลูกค้าส่วนใหญ่ไม่ได้อยู่ใน workspace ถ้าใช้ person ทุกแถวจะว่าง ให้ใช้ select ที่ประกาศตัวเลือกไว้ล่วงหน้า ผลที่ตามมาคือไม่มีการแจ้งเตือนรายบุคคล และการเพิ่มคนใหม่ต้องไปเพิ่มตัวเลือกก่อน
- **เฟส เป็น select ประกาศครบตั้งแต่วันแรก** — ตัวเลือกของ select ต้องมีอยู่ก่อนถึงจะเลือกใส่แถวได้ ตอน kickoff งานเกือบทั้งหมดเป็นของเฟสแรก แต่ให้ประกาศตัวเลือกครบทุกเฟสในตารางแผนเฟสตั้งแต่ตอนสร้าง งานของเฟสหลังที่เข้ามาทีหลังจะได้เลือกได้ทันทีโดยไม่ต้องไปแก้โครงสร้าง database ก่อน
